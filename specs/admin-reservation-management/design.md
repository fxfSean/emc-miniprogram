# 管理员预约管理技术设计

## 1. 设计目标

在不引入新集合、不改变普通用户登录模型的前提下，复用现有预约、设备禁用时段和规则数据，为管理员补齐预约总览与干预能力。所有敏感读写继续经云函数完成，客户端不直接访问业务集合。

## 2. 模块边界

### 小程序页面

新增 4 个管理员页面：

1. `pages/admin/reservations`
   - 日历/列表切换
   - 设备与日期筛选
   - 预约状态展示
   - 预约详情底部抽屉
   - 管理员取消预约入口
   - 进入代预约、禁用时段、规则配置
2. `pages/admin/reservation-create`
   - 搜索并选择已通过用户
   - 选择设备与日期
   - 展示 30 分钟时段
   - 填写事由并代预约
3. `pages/admin/device-blocks`
   - 按设备查看禁用/维护时段
   - 新增禁用时段
   - 删除禁用时段并恢复开放
4. `pages/admin/reservation-rules`
   - 编辑四项预约规则
   - 展示单位、范围和当前值

现有 `pages/admin/index` 新增“预约管理”入口；现有 `pages/reservation/create` 改为动态展示规则文案。

### 云函数

- `admin`：管理员总览查询、预约详情、禁用时段管理、规则读写。
- `reservation`：继续集中处理预约创建和取消；新增管理员代预约与管理员取消，确保普通预约和代预约复用同一套冲突与配额校验。
- `user`、`device`：接口不变。

## 3. UI 设计规范

### 目的

让管理员在一个入口内完成“看全局、查详情、做干预、改规则”，并将高风险操作与日常浏览清晰分层。

### 视觉方向

采用 Industrial/utilitarian（工业化、实用主义）调度台风格，延续现有实验室管理端视觉语言。

### 色彩

- 品牌深绿：`#176B5B`
- 浅绿状态底：`#E8F2EF`
- 页面背景：`#F7F8FA`
- 边界灰：`#E3E7E5`
- 危险红褐：`#B64A43`

### 字体

沿用微信小程序原生苹方体系；统计数字可使用 `Georgia`。不引入网络字体、Emoji 图标或额外组件库。

### 布局

- 顶部为标题、视图切换和横向筛选带。
- 日历作为主视觉，所选日期预约列表从下方衔接。
- 列表视图使用左侧时间轴、右侧预约信息的不对称结构。
- 预约详情与新增禁用时段使用底部抽屉。
- “代预约”为突出主操作；取消、删除禁用时段等危险操作位于详情末端并二次确认。

## 4. 管理员 API 设计

所有接口先校验调用者为 `role = ADMIN` 且 `status = APPROVED`。

### `admin.reservationCalendar`

请求：

```json
{ "month": "2026-08", "deviceId": "可选" }
```

返回：指定月份每天的预约总数，以及当前筛选范围内的设备列表。按 UTC+8 计算日期。

### `admin.listReservations`

请求：

```json
{
  "startAt": 1785513600000,
  "endAt": 1788192000000,
  "deviceId": "可选",
  "page": 1,
  "pageSize": 20
}
```

返回：分页预约摘要、总数。摘要包含预约 ID、设备、预约人、日期、时段、动态状态和事由摘要。

限制：单页最多 50 条；最大查询区间 366 天。

### `admin.reservationDetail`

请求：`{ "id": "预约ID" }`

返回预约人姓名/学号、设备名称/编号、日期、时段、事由、动态状态、创建时间和取消审计信息。不返回 `openid`。

### `admin.listDeviceBlocks`

请求：设备 ID、起止时间和分页参数；返回禁用时段及设备摘要。

### `admin.createDeviceBlock`

请求：

```json
{
  "deviceId": "设备ID",
  "startAt": 1785513600000,
  "endAt": 1785600000000,
  "category": "MAINTENANCE",
  "reason": "设备维护"
}
```

约束：开始早于结束、最长 31 天、设备存在、不与有效预约或现有禁用时段重叠。

### `admin.deleteDeviceBlock`

请求：`{ "id": "禁用时段ID" }`。删除后对应时段恢复开放，并记录操作日志到云函数日志；本期不新增独立审计集合。

### `admin.getReservationSettings`

返回规范化规则；缺失字段使用安全默认值。

### `admin.saveReservationSettings`

请求字段及范围：

- `maxDailyMinutes`：30–1440，30 的整数倍
- `maxActiveReservations`：1–20
- `maxAdvanceDays`：1–90
- `cancelDeadlineMinutes`：0–10080

保存时仅更新上述字段，保留 `inviteCode`、最短/最长预约时长等现有配置。

## 5. 预约 API 扩展

### `reservation.adminCreate`

请求：目标用户 ID、设备 ID、日期、开始时间、结束时间、预约事由。

处理流程：

1. 校验调用者为管理员。
2. 校验目标用户为已通过审核的普通用户。
3. 复用普通创建预约的时间、设备、配额、禁用时段和冲突校验。
4. 使用现有 `reservation_locks/{deviceId}_{date}` 事务锁防止并发冲突。
5. 写入预约归属目标用户，并增加代预约审计字段。

### `reservation.adminCancel`

请求：预约 ID、取消原因。

约束：仅动态状态为“待使用”或“使用中”的 `BOOKED` 预约可取消；不检查普通用户取消截止时间。写入取消管理员、时间、原因和来源。

### 普通接口调整

- 普通用户 `cancel` 增加取消来源与取消人审计字段。
- `availability` 增加规范化规则值，预约页面据此动态生成须知。
- 普通 `create` 与 `adminCreate` 调用同一内部创建函数，避免规则漂移。

## 6. 数据模型

### `reservations` 新增可选字段

```json
{
  "bookingSource": "USER | ADMIN",
  "bookedByAdminId": "管理员用户ID",
  "cancelSource": "USER | ADMIN",
  "cancelledByUserId": "操作用户ID",
  "cancelReason": "取消原因"
}
```

兼容策略：历史预约缺少上述字段时按普通用户创建、无取消原因展示。

### `device_blocks` 规范字段

```json
{
  "deviceId": "设备ID",
  "startAt": 1785513600000,
  "endAt": 1785600000000,
  "category": "MAINTENANCE | HOLIDAY | OTHER",
  "reason": "原因",
  "createdBy": "管理员用户ID",
  "createdAt": "服务端时间",
  "updatedAt": "服务端时间"
}
```

历史记录缺少 `category` 时按 `OTHER` 展示。

### `settings/reservation`

继续使用现有文档，不新增集合。规则缺失时使用：

```json
{
  "maxDailyMinutes": 240,
  "maxActiveReservations": 3,
  "maxAdvanceDays": 7,
  "cancelDeadlineMinutes": 30
}
```

## 7. 一致性与并发

- 普通预约和代预约使用相同的按设备/日期锁文档。
- 创建禁用时段时，事务内触碰所覆盖日期的相同锁文档，再检查预约与禁用时段冲突并写入；最多覆盖 31 天。
- 取消预约通过条件更新前再次读取状态，避免重复取消。
- 所有时间由云函数校验，客户端时间只用于交互展示。

## 8. 查询与索引

保留现有索引，并补充：

- `reservations`: `startAt` 升序
- `reservations`: `deviceId` 升序、`startAt` 升序
- `device_blocks`: `startAt` 升序

查询结果由云函数分页，不把整库预约一次性返回客户端。日历统计只查询一个自然月。

## 9. 权限与隐私

- 数据库集合继续使用“仅管理员可读写”预设，客户端通过云函数访问。
- 管理员接口每次调用均服务端校验角色和状态。
- 预约总览仅返回姓名、学号等管理所需字段，不返回 `openid`、手机号等无关信息。
- 云函数不得返回完整 `event`、`context` 或运行环境变量。

## 10. 错误与交互

- 筛选请求采用请求序号，避免快速切换时旧响应覆盖新结果。
- 所有写操作防重复提交，并在成功后刷新当前视图。
- 管理员取消、删除禁用时段必须二次确认。
- 规则保存成功后返回规范化值，页面以服务端结果回填。
- 云函数返回可操作的业务错误，不向客户端暴露堆栈。

## 11. 验证策略

### 静态验证

- Node.js 语法检查全部云函数和页面脚本。
- WXML 标签结构与 WXSS 编译检查。
- UI 禁用色、字体、Emoji 自审计。

### 最小业务用例

1. 管理员按月查看预约数量并按设备筛选。
2. 查看预约详情，确认事由仅管理员可见。
3. 管理员为用户代预约，普通用户“我的预约”可看到记录。
4. 对冲突时段代预约，系统拒绝第二笔。
5. 管理员取消待使用预约，记录取消原因；普通用户看到“已取消”。
6. 新增与预约冲突的禁用时段失败；无冲突时成功并在预约页显示不可选。
7. 删除禁用时段后恢复可预约。
8. 修改四项规则后，后端校验和预约须知同步更新。

## 12. 部署顺序

1. 本地完成代码与静态验证。
2. 创建/确认新增数据库索引。
3. 部署 `admin`、`reservation` 云函数。
4. 在开发环境执行最小业务用例。
5. 小程序本地编译与真机/模拟器回归；本任务不自动上传体验版或发布正式版。
